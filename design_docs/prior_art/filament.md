# Filament (Nigam, Azevedo de Amorim, Sampson — PLDI 2023, "Modular Hardware Design with Timeline Types")

How the paper specifies the semantics of its language, read for what Copper can
borrow. Section/figure numbers are the paper's. Page numbers are the PDF's
(the PACMPL preprint numbering, 1–30).

Sources: text `scratchpad/papers/filament_pldi2023.txt`; PDF

---

## 0. One-paragraph verdict

Filament's "semantics" is **not a value semantics**. It is a *log-transformer*
denotation (§6.1, Fig. 7b, Fig. 9, App. A.2): a command denotes a function from
logs to logs, where a log maps each *event* (= clock cycle, `T`, `T+1`, …) to
the **set of ports read** and the **multiset of ports written** in that cycle.
No data values appear anywhere. The only properties the model can express are
"a port is read in a cycle in which it is written" and "no port is written
twice in one cycle" (Def. 6.1), plus the same under pipelined re-execution
(Def. 6.2). The semantics exists to give the separation-logic-style type system
(§6.2, App. A.3) something to be sound against (Thm. 6.3 / A.5). The *meaning
of the data* — what a register does, what `out = a + b` computes — is delegated
entirely to the compilation chain (Low Filament → Calyx → Verilog, §5) and to
the extern Verilog primitives; nothing is proven about that chain. The
empirical check is a cocotb harness that drives inputs only inside the declared
availability intervals (§7.1) plus differential fuzzing against a reference
(App. B.1).

## 1. Object given a semantics; grammar

**Object:** a *simplified core calculus* ("we used a simplified version of
Filament for our formalization", App. A.1, p.25): every component is
parameterized by **exactly one event** with a delay, and there are **no
ordering constraints** between events (so none of the `where L > G` externs of
§3.6). The authors argue nothing is lost because user-level components cannot
make events interact ("functionally equivalent to multiple components with
disjoint events", A.1). Multi-event *external* components are explicitly "not
supported in our formalism" (§6, p.15). The surface language (§3: components,
instances, invocations, connections, `@interface` ports, phantom events,
`extern`, parametric delays `L-G`) is not what is formalized; neither is Low
Filament (§5.1, "an untyped extension").

**Grammar** (Fig. 7a, p.15; repeated App. A.1, p.25):

```
x, C ∈ vars    t ∈ events    p, q ∈ ports

M ::= def C⟨t : n⟩(p1 : π1, …, pj : πj){ c }        component: one event t with delay n,
                                                    ports with availability intervals
c ::= c1 • c2                                       parallel composition
    | pd = ps                                       connection (wire)
    | x := new C                                    instantiation
    | x := invoke x⟨T⟩(p1, …, pj)                   invocation of instance x at event T

T ::= t | T + n                                     event expressions (cycle offsets)
π ::= [T1, T2]                                      availability interval

τ ::= ∀⟨t : n⟩(p1 : π1, …, pj : πj)                 component type (A.3)
Γ ::= · | Γ, C : τ | Γ, p : π                       type context (components, ports)
Δ ::= · | Δ, t : n                                  delay context
Λ ::= · | Λ, I : π | Λ, p : π                       timeline (resource) context
```

Note the inconsistency: the grammar writes `π ::= [T1, T2]` (closed), while
every prose interval is half-open `[G, G+1)` (§3.2). The intended reading is
"the cycles T1 … T2−1".

There is no expression language: no arithmetic, no conditionals, no data.
`invoke` carries port *names*, not expressions. The program is a list of
`def`s; "the semantics of a program is the log generated by executing a
distinguished `main` component with the empty log" (§6.1).

## 2. Style of the semantics

**Primary: denotational, over logs, with no values** ("log-based semantics of
hardware", §1 contributions; "defined as functions over logs", §6.1). Each
command is `⟦c⟧ : L → L` where `L = T → R × W`. The authors call it a
"log-transformer semantics" (Fig. 7b caption, Fig. 9 caption).

It is closer to an **abstract interpretation / resource-usage semantics** than
to a denotational semantics in the Scott sense: it tracks *which ports are
touched when*, as a stand-in for "is this value semantically valid" and "is
this physical resource used twice". The paper is explicit that this is a
deliberate abstraction: "While in real hardware, values are always available on
a port or a wire, Filament's semantics only track semantically valid values
from a read. Usage of hardware resources is denoted by a write, and it is
physically impossible to write two values to a port" (A.2, p.26).

**Secondary: type-system-only with semantics-by-translation.** The real
"meaning" of a design is what Calyx emits (§5.3), and the type system is where
the engineering content is (§4, §6.2, A.3). The connection between the type
system and the log model is the soundness theorem (Thm. 6.3 / A.5).

There is **no operational semantics**, no stream/function-over-time
denotation of values, and no simulator semantics.

## 3. Time model

- **Events are clock cycles with a symbolic origin.** `T ::= t | T + n`; "if G
  occurs at clock cycle i, then G + n occurs at clock cycle i + n" (§3.1).
  Adding two event variables is disallowed ("meaningless", §3.1). All events are
  in one clock domain (fn. 2).
- **Availability intervals** `@[T1, T2)` on ports: for an input inside a
  component body the interval is a *guarantee*, for an output a *requirement*;
  at a use site the polarity flips (§3.2).
- **Delay** `⟨G : n⟩` = initiation interval. "Timeline interpretation": an event
  with delay n denotes "any infinite sequence of 1 cycle long clock pulses such
  that each pulse is at least n cycles apart" (§3.1, Fig. 3a). This is the
  universe quantified over for safe pipelining.
- **Unit of observation in the log: one cycle = one event; per event, a set of
  ports read and a multiset of ports written.** No value per port per cycle —
  only presence/absence. No sub-cycle structure, no delta cycles, no phases.
- **Interface port / `go`:** the physical signal that reifies an event at run
  time (§3.2). In the log of a component definition, the delay window is
  recorded as writes to `go` in every cycle of `[G, G+d)` (A.2 example, p.26):
  the multiplier `mul⟨G:2⟩` has `G → ({l, r}, {go})`, `G+1 → (∅, {go})`,
  `G+2 → (∅, {out})`. So *resource occupancy is encoded as a write to the
  interface port*, and a conflict shows up as a duplicate write.

Definition 4.1 (Initiation Interval), §4.3: "Let P(t) be the execution of
pipeline P at time t. P(t0) ⊥ P(t1) states that the pipeline executions at t0
and t1 do not have resource conflicts. I is a valid initiation interval iff
∀n ≥ 0. P(t) ⊥ P(t + I + n)." (They reject the alternative ∀k≠0. P(t) ⊥
P(t + k·I) as less compositional.)

## 4. State: registers vs wires, initial values

**There is no notion of state in the semantics.** A register is an *extern
component with a latency signature* (§3.6, §5.4):

```
comp Register<G: L-(G+1), L: 1>(@interface[G] en: 1, @[G, G+1] in: 32)
  -> (@[G+1, L] out: 32) where L > G+1;
comp Delay<G: 1>(@[G, G+1] in: 32) -> (@[G+1, G+2] out: 32);
comp Prev[SAFE]<G: 1>(@interface[G] en: 1, @[G, G+1] in: 32) -> (@[G, G+1] out: 32);
```

i.e. "a register's signature captures its timing behavior — the output is
available one cycle after the input" (§2.3). `Register` can hold for an
arbitrary window `[G+1, L)` via `en`; `Delay` holds for exactly one cycle;
`Prev` is "simply a register but Filament gives it a different type
signature—it allows access to the output in the same cycle when the input is
provided which corresponds to reading the previous value in the register"
(§7.2). What decides "stateful" is therefore nothing in the calculus: it is
whichever extern you instantiate. Connections are "continuously active wires"
(§3.5).

**Initial/reset values:** absent from the semantics. The only mention is the
`SAFE` compile-time parameter on `Prev`, "to indicate whether the first read
produces an undefined value" (§7.2), and `Prev[32, 0]` in the systolic array
(App. B.1) which reads as "use 0 if acc does not contain a valid value". No
reset port, no `initial`, no X.

In the log model, a register's *sequential* nature is invisible: `Register`'s
log is just `G → ({in}, {go})`, `G+1.. → (∅, {out})`. The "state" is the
one-cycle shift of the write set.

## 5. Intra-cycle ordering

- **No ordering within a cycle.** Composition `c1 • c2` is parallel: "Composition
  reflects the parallel nature of hardware—it simply unions the two logs
  together" (§6.1). Program text order is irrelevant.
- **Multiple writes to a port in one cycle are a conflict**, detected as the
  multiset having a duplicate (`Ws ≠ W`, Def. 6.1). The type system prevents
  this with the separating split on instance timelines (A.3). There is no
  last-write-wins, no priority.
- **Reads must be "covered":** `R ⊆ Ws` per event. There is no forwarding
  question: a read in cycle T sees whatever is written in cycle T, full stop;
  "combinational" vs "registered" is entirely in the interval arithmetic
  (`[T, T+1)` out vs `[T+1, …)` out).
- **Guarded assignment in Low Filament** (§5.1): `in = g1 ? out; in = g2 ? out;`
  — "Calyx's well-formedness condition requires that only one of the guards is
  active at a time for any given source port", and the compiler synthesises
  guards `Gf._s || … || Gf._e` from intervals (§5.2) that are disjoint "since
  the program is well-typed".
- **Combinational loops:** not addressed. Related work explicitly defers to
  "wire sorts [14] check whether module composition can create combinational
  loops, both of which are orthogonal to Filament's guarantees" (§8).

## 6. Properties stated and how they are established

| Claim | Where | Technique | Status |
|---|---|---|---|
| Def. 6.1 / A.1 **Well-formedness** of a log: per event, `Ws = W` (no conflicting writes) and `R ⊆ Ws` (reads ⊆ writes) | §6.1, A.2 | definition | — |
| Def. 6.2 / A.2 **Safe pipelining**: for event T with delay d, ∀n ≥ d, `⟦M⟧_T ∪ ⟦M⟧_{T+n}` is well-formed | §6.1, A.2 | definition | — |
| §4.1 "delay ≥ every interval mentioning the event ⇒ no overlap of a port's intervals across re-executions" | §4.1 | 3-line paper argument (`I_{t+n} − I_t ≥ d`, `|I_t| ≤ d`) | informal |
| **Lemma A.3 (Availability Soundness)**: if `Δ;Λ;Γ ⊢ c ⊣ Λ';Γ'` then for every log L and event T, `p ∈ W` of `⟦c⟧(L,T)` iff `p ∈ π2(L(T))` or `T ∈ Λ(p)` | A.4 | induction on typing derivation, prose | paper proof |
| **Corollary A.4 (Disjoint Writes)**: for well-typed `c1 • c2`, `W1 − L` and `W2 − L` are disjoint | A.4 | from A.3 + disjoint Λ | paper |
| **Theorem 6.3 / A.5 (Soundness)**: if `Δ;Λ;Γ ⊢ c ⊣ Λ';Γ'` and L is well-formed then `⟦c⟧ L` is well-formed | §6.2, A.4 | induction on typing derivation, 4 cases, prose | paper proof |

Observations:

- **Only well-formedness is proven.** "Our type system guarantees theorem
  focuses on the well-formedness property (Section 4.2)" (A.4). *Safe
  pipelining* (Def. 6.2) is defined but no theorem connects the §4.4 checks
  ("Triggering Subcomponents", "Reusing Instances") to it; §4.4 says only "The
  following checks are sufficient to prove this."
- The main-text statement of Thm 6.3 ("then ⟦c⟧ is well-formed") is sloppy —
  `⟦c⟧` is a function, not a log; A.5 has the correct conditional form (and a
  typo, "⟦c⟧ − L").
- **The invocation typing rule is only sketched** (A.3, p.27): three premise
  groups "valid reads / no conflicts / safe pipelining", shown as fragments
  (`Γ(p1) ⊆ π1', …`, `Λ(I) = π ∧ [T, T+n] ⊆ π`, `E(T) = t' ∧ Δ(t') ≥ Δ(t)`),
  not as one rule. §6.2 says "The invocation rule (not shown)".
- **Nothing is mechanized.** No Coq/Lean/Isabelle. The proofs are half a page.
- Nothing is said about determinism, races, or absence of combinational loops;
  nothing about values, so functional correctness is out of scope by
  construction.

## 7. Relation to the generated hardware

- Pipeline: Filament → (type check §4) → Low Filament (§5.1: explicit `fsm F[n]
  (trigger)`, explicit interface-port assignments, guarded assignments) →
  Calyx (§5.3) → Verilog (by the Calyx compiler). Fig. 6.
- **No correctness statement for the lowering.** The strongest sentence is
  "Since Filament guarantees that the generated guards are disjoint, we can be
  sure that Calyx will generate correct FSMs" (§5.3) — an appeal to Calyx's
  well-formedness condition, not a theorem. The FSM is "simply a sequence of
  registers connected together".
- **Testing / reference comparison:**
  - §7.1 "Cycle accurate harness": a generic cocotb harness that (1) provides
    inputs for exactly the cycles in the signature, (2) pipelines using the
    delays, (3) captures outputs in the declared intervals. Used to find that
    Aetherling reports wrong latencies for 5/14 designs and that one design
    "breaks its own interface" (needs input held 6 cycles, declares 1).
  - App. B.1: a pipelined FP adder from GitHub was translated to Filament and
    checked by "a fuzzing harness to ensure that the outputs of the
    implementation matched to the source" — "differential testing of the
    combinational, pipelined, and Filament implementations".
  - App. B.2: PipelineC designs' signatures validated differentially against
    the B.1 unit.
- There is **no separate Filament simulator**; the only executable meaning is
  the Verilog. So "sim ≡ synthesized" is not a question the paper can ask.

### 8.1 Log-transformer semantics (Fig. 9, p.25)

```
⟦c⟧ : Log → Log                            (Log = T → R × W)
⟦x := new C⟧            = id
⟦pd = ps⟧               = λ(R, W). if ps ∈ W then (R{ps/pd}, W) else (R, W)
⟦c1 • c2⟧               = ⟦c1⟧ ∪ ⟦c2⟧
⟦x1 := invoke x2⟨T'⟩(q1, …, qm)⟧ = ⟦connects(x1, [q1, …, qm])⟧ ∘ ⟦x2⟧

⟦M⟧ : P
⟦def C⟨t : n⟩(i0 : π0, …, o0 : πi, …){c}⟧ = {π0 ↦ i0, …} × {πi ↦ o0, …}
```

with (A.2, p.26) `connects(x1, [q1, …, qm]) = (x1.p1 = q1); …; (x1.pm = qm)`,
"implicitly assuming that the ports x1.pi have not been used". The Fig. 7b
form of the connection case makes the map explicit:
`⟦pd = ps⟧(L) = map(λ(R,W). if ps ∈ W then (R{ps/pd}, W) else (R, W), L)`.

Reading: a component definition yields a *partial log* that puts each input
port into the read set for every event in its interval and each output port
into the write set for every event in its interval (A.2: "the input ports are
added to the reads (R) and the output ports to the writes (W) for each event
contained in their corresponding availability interval"). A connection renames
the destination to the source in the read set wherever the source is written —
so an unconnected/unavailable destination survives as a dangling read and
breaks `R ⊆ W`. An invocation composes the instance's log with the
connections. Composition unions. The text and figure disagree on whether
reads are a set or a multiset ("set of ports that are read from (R) and a
multiset of ports that are written to (W)" in §6.1 vs "multisets of reads (R)
and writes (W)" in Fig. 9's caption); only W's multiplicity matters.

Worked logs (A.2, p.26):

```
⟦def add⟨G:1⟩(l:[G,G+1], r:[G,G+1], out:[G,G+1])⟧ = G   → ({l, r}, {go, out})
⟦def mul⟨G:2⟩(l:[G,G+1], r:[G,G+1], out:[G+2,G+3])⟧ = G   → ({l, r}, {go})
                                                       G+1 → (∅, {go})
                                                       G+2 → (∅, {out})
```

### 8.2 Well-formedness and safe pipelining (Def. 6.1/6.2, A.1/A.2)

```
Def 6.1  A log L is well-formed iff for each event:
           • no conflicting writes:  Ws = W   (Ws = deduplicated W)
           • reads ⊆ writes:         R ⊆ Ws
         A component M is well-formed iff its log is.

Def 6.2  If M has event T with delay d and ⟦M⟧_G is its log with T renamed to G,
         M is safely pipelined iff for every n ≥ d the log
           L_n = ⟦M⟧_T ∪ ⟦M⟧_{T+n}
         is well-formed.
```

### 8.3 Typing judgement, separating split, composition (Fig. 7c; A.3)

```
Judgement:   Δ; Λ; Γ ⊢ c ⊣ Λ'; Γ'
   Γ : types of components/instances + availability of ports (reusable)
   Δ : delay of each event
   Λ : timeline/resource context — availability interval of each instance
       (consumed when used in a cycle) and port

Separating split:
   Λ = Λ1 ∗ Λ2  iff  ∀(I : π) ∈ Λ ⇒ ∃π1, π2. (I : π1) ∈ Λ1 ∧ (I : π2) ∈ Λ2
                                          ∧ π1 ∩ π2 = ∅ ∧ π1 ∪ π2 = π

(Instantiate)          Γ(C) = τ    Γ' = Γ, I : τ    Λ' = Λ, I : [0, ∞)
                       ──────────────────────────────────────────────
                             Δ, Λ, Γ ⊢ I := new C ⊣ Λ', Γ'

(Connection)                     Λ(pd) ⊆ Γ(ps)
                       ──────────────────────────────────
                          Δ, Λ, Γ ⊢ pd = ps ⊣ Λ, Γ
   "the source port is available for at least as long as the destination requires"

(Composition)   Δ, Λ1, Γ ⊢ c1 ⊣ Λ1', Γ1      Δ, Λ2, Γ ⊢ c2 ⊣ Λ2', Γ2
                ───────────────────────────────────────────────────────
                  Δ, Λ1 ∗ Λ2, Γ ⊢ c1 • c2 ⊣ Λ1' ∗ Λ2', Γ1 ∪ Γ2
   (same Γ for both: ports defined anywhere are visible everywhere — this is
    what makes order irrelevant)

(Invoke — three premise groups, only fragments given, A.3 p.27)
   valid reads:
      Γ(I) = ∀⟨t:n⟩(p1:π1, …, pj:πj)     Γ(q1) = π1, …, Γ(qj) = πj
      π1' = π1[t/T], …, πj' = πj[t/T]     Γ(p1) ⊆ π1', …, Γ(pj) ⊆ πj'
      Γ' = x.{p1:π1', …, pj:πj'}         Γ'' = Γ ∪ Γ'
   no conflicts:
      Γ(I) = ∀⟨t:n⟩(…)     Λ(I) = π     [T, T+n] ⊆ π
   safe pipelining:
      Γ(I) = ∀⟨t:n⟩(…)     E(T) = t'     Δ(t') ≥ Δ(t)
   ─────────────────────────────────────────────────────────
      Δ, Λ, Γ ⊢ x := invoke I⟨T⟩(q1, …, qj) ⊣ Λ, Γ''
```

(The "valid reads" premise is written with `Γ(p) ⊆ π'`; the intended direction
is "argument available ⊇ parameter required", matching the connection rule.)

### 8.4 Soundness (A.4)

```
Lemma A.3 (Availability Soundness).  If Δ;Λ;Γ ⊢ c ⊣ Λ';Γ', then for every log
  L and every event T, with (R, W) = ⟦c⟧(L, T):  p ∈ W  iff  p ∈ π2(L(T)) or T ∈ Λ(p).

Corollary A.4 (Disjoint Writes).  If Δ;Λ;Γ ⊢ c1 • c2 ⊣ Λ';Γ', then for
  (R1,W1) = ⟦c1⟧(L) and (R2,W2) = ⟦c2⟧(L), W1 − L and W2 − L are disjoint.

Theorem A.5 (Soundness).  If Δ;Λ;Γ ⊢ c ⊣ Λ';Γ' then if L is well-formed,
  ⟦c⟧ L is well-formed.
  Proof: induction on the typing derivation — Instantiate (identity),
  Connection (pd ∈ R or not; availability ⊆ ⇒ ps ∈ W), Comp (union is
  monotone + A.4 disjointness), Invoke (new writes are the output ports, a
  set; placeholder reads removed by connects, each connection well-typed).
```

### 8.5 Phantom check (Def. 5.1, §5.4)

A phantom event G (no interface port) is used correctly if (1) it is not used
to share any instances, (2) it is only used to invoke subcomponents that use
phantom events. Compilation then emits no FSM and no guards.

## 9. Transfer to Copper — what fits, what does not

### 9.1 Devices that fit

1. **A per-cycle log as the denotation.** `L = T → R × W` is the right *shape*
   for Copper's "one value per signal per cycle": replace the read set / write
   multiset with `Cycle → (Signal → Value)` (or, keeping Filament's two
   components, `Cycle → (Reads : Signal ⇀ Value) × (Writes : Signal ⇀ Value)`).
   The point to keep is that **the denotation is indexed by the cycle, not by
   program position**, so statements inside a segment have no order in the
   model. This is exactly the discipline Copper's rules enforce after the fact
   (`multi_write_collapse`, the alignment family): a segment's writes to a
   port must collapse to one value per cycle. In Filament this is a
   *definition* (multiset conflict), in Copper it is a *check on a sequential
   program*; a Copper semantics should state it as the definition and present
   the rules as the sufficient conditions.

2. **Event arithmetic `T + n` for cycle offsets.** Copper's "the k-th tick after
   loop entry" is `G + k`; the `pc` FSM state is the index k into a bounded
   window. For the *linear* (no `match pc`) route this is literally
   Filament's model: a body with ticks at positions 0..m is a component with
   event G and the segment between tick i and tick i+1 is "available in
   `[G+i, G+i+1)`".

3. **The register signature as the RegOut rule.** `Register: in @[G, G+1) →
   out @[G+1, L)` is the sentence "a RegOut write takes effect at the first
   clock edge after it executes" (tick-dialect decision 2026-10-23). Copper
   could state the RegOut port's denotation as `out(c+1) = last write in
   segment ending at edge c, else out(c)` — a one-cycle shift of the write log
   plus hold. Filament's `Register` vs `Delay` vs `Prev` triple is also a
   useful vocabulary: `RegOut` = Register (holds via enable), a `let` live
   across one tick = Delay, and Copper's "read of committed state at the
   opening" = Prev (same-cycle read of the previous value).

4. **Safe pipelining as a definition over logs** (`⟦M⟧_T ∪ ⟦M⟧_{T+n}`
   well-formed): Copper's loop iteration re-entry is the n = 1 case
   (initiation interval 1, every iteration overlaps the next at the back
   edge). The trailing-drive rules (`trailing_regout_reads_input`,
   `trailing_out_reads_input`) are statements about `⟦body⟧_T ∪ ⟦body⟧_{T+m}`
   where m is the body length — a write in the trailing segment of iteration
   k and a read in the opening segment of iteration k+1 land in the same
   cycle. Filament's "union two shifted copies" is a clean way to *define*
   what a loop means without unrolling infinitely (contrast Anvil's unrolling
   lemma).

5. **Reads ⊆ writes per cycle as the "semantically valid" criterion.** Copper's
   simulator has freshness guards on reads (per-read freshness in the macro);
   Filament's `R ⊆ Ws` is the static version. If Copper ever wants to say
   "reading an Out port the module did not drive this cycle is an error", this
   is the sentence.

6. **The testing posture.** A harness that "provides inputs for exactly the
   cycles specified" and "captures outputs in the intervals provided" is the
   interval-aware version of Copper's sweep. Copper's sweep already covers
   "every initial input vector"; Filament's timeline interpretation ("any
   pulse train at least d apart") is the analogue for *re-trigger* patterns
   and could motivate a sweep sequence family that re-enters the loop at every
   offset.

### 9.2 Devices that do not fit, and why

1. **No values ⇒ cannot state Copper's correctness bar.** Copper's whole
   claim is "simulator and SystemVerilog agree cycle for cycle on values".
   Filament's model cannot express "the value of `out` in cycle 3", so neither
   "sim ≡ SV" nor any of the D1/multi-phase divergences (which are about
   *which* value is observed, one cycle early or late) can be stated in it.
   Borrow the shape, not the content.

2. **No intra-cycle structure at all.** Filament has no sequential statements,
   so the opening-vs-closing anchor question — the entire pre-tick alignment
   family — has no counterpart. A read in cycle T sees "the" value in cycle T.
   Copper's problem is precisely that a *sequential* body with reads and
   writes interleaved before a tick must be given a *parallel* meaning; that
   is a problem Filament sidesteps by having only parallel composition. The
   Copper semantics must add what Filament lacks: a rule mapping statement
   position within a segment to an anchor (opening edge vs closing edge).
   Filament's "Prev vs Register" split is a hint that the anchor can be
   carried in the *type of the read*, not in the position.

3. **Static schedules only.** Filament rejects dynamic timing ("Extending
   Filament with safe dynamic pipelines is an avenue for future work", §4.4;
   "all delays evaluate to compile-time constants"). Copper's
   `control_extract` route (`match pc` with data-dependent branches, wait
   loops, `break` inside a counted `for`) is dynamic. The `T + n` arithmetic
   covers the linear route only; the extracted route needs Anvil's event
   graph or a stream semantics.

4. **Explicit instantiation vs inferred registers.** In Filament every state
   element is a named instance of an extern with a signature; Copper infers
   registers by liveness across ticks (`infer_registers`). A Filament-style
   semantics would need registers to be objects in the syntax. The usable
   alternative: define the denotation on the *post-inference* IR (CHIR/SHIR,
   where registers are explicit) and prove/test that inference is a
   meaning-preserving translation from the source. Filament itself does
   exactly this move for invocations ("compiled away", §2.2; Low Filament
   makes them explicit) — the formal calculus is the surface, but the
   compiler's explicit form is what the proof cases reason about.

5. **Validity intervals vs hold.** In Filament a port not written in cycle T is
   *invalid* in T; in Copper a sequential `Out` unwritten in a cycle *holds*
   its previous value (enabled-register idiom, anchored against BaseJump
   `bsg_dff_en`). These are opposite defaults. Do not import Filament's
   `R ⊆ Ws` as a definedness rule for `Out`; Copper's hold is the definition,
   and the `_hold` register of phase C is its emission.

6. **No reset/initial semantics.** Filament has nothing to say about
   power-on values; Copper has a decided rule (constant initializer →
   `initial`, X otherwise, `COPPER_VERILATOR_X_INITIAL`). Nothing to borrow.

7. **Proof bar is low.** Half-page paper induction on a four-rule calculus
   with the invocation rule unstated; safe pipelining never proven. If Copper
   writes "formal-esque" definitions, matching Filament's rigor is not hard;
   the lesson is rather *what they chose to leave unproven* — the lowering —
   which is exactly where Copper's bugs have lived (edge-form staging, `ff`
   MemIndex muxes, hold forms). Copper's differential sweep is the thing
   Filament does not have; a Copper semantics should be written so that the
   sweep is a test of the semantics' two realizations, not of each other.

### 9.3 Concrete suggestion

Write Copper's denotation as a valued log on the post-inference IR:

```
⟦M⟧ : (Cycle → In → Value) → (Cycle → Port → Value)
Reg(c+1) = commit(segment that ends at edge c)      -- Filament Register / RegOut
Out(c)   = drive(c) if driven in c else Out(c−1)     -- hold (NOT Filament's R ⊆ W)
```

with every read in a segment tagged by an anchor: `opening(c)` (the value of
the signal during cycle c as the simulator observes at segment entry) or
`closing(c)` (the value at the edge ending c). Filament's interval `[G+i,
G+i+1)` is the cycle c; its `Prev` is `opening`, its `Register` is the
`c+1` shift. State the sweep's property as `log_sim = log_SV` on this type.
