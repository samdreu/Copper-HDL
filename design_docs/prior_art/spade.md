# Spade — Skarman & Gustafsson, "Spade: An Expression-Based HDL With Pipelines", FPL 2022 (arXiv 2304.03079; also OSDA 2023)

Source: paper/references/spade_fpl2022.pdf (text: scratchpad/papers/spade_fpl2022.txt).
Sections: II Related Work, III Basic Semantics (A Pipelines, B Types, C Memories), IV
Ports (linear types), V Spade Software (A compiler, B tooling, C test benches), VI
Conclusions. Listings 1–8, Figs. 1–3.

## 1. What is given a semantics; grammar; what defines meaning in practice

- **Object:** the standalone Spade surface language (own lexer/parser, §V-A). Units are
  `entity` (may contain sequential logic), `fn` (combinational only), `pipeline(depth)`
  (§III). The section is titled "Basic Semantics" but is an example walk-through of
  Listing 1 (the LED blinker) and Listing 2 (the pipeline).
- **Grammar:** none in the paper. §V-B mentions "a tree-sitter grammar" for editors.
- **IRs:** §V-A: AST → HIR ("retains the tree structure of the AST but resolves names and
  scoping rules, and performs initial semantic analysis"; type inference and linear type
  checking run on HIR) → MIR ("the tree structure is flattened to a list of simple
  statements") → SystemVerilog ("a slim subset"). CIRCT/LLHD/Calyx named as possible
  future backends.
- **What defines meaning in practice: the generated SystemVerilog, simulated by someone
  else's simulator.** §V-C: "The Spade language itself is designed primarily for hardware
  description and synthesis, rather than simulation. ... Spade tests are written using
  cocotb ... while Verilog generated by the compiler is simulated with off-the-shelf
  Verilog simulators." Spade has **no simulator of its own**. The compiler is exposed as a
  Python module only to *evaluate Spade expressions to bit vectors* for stimulus and
  expected values (Listing 8, lines 9–13: `s.i.memory_command = "Command::Write(10)"`,
  `s.o.assert_eq("10")`): "parts of the Spade compiler are exported as a Python module
  which reads the stored state, then compiles and evaluates the expressions used in the
  test bench. The resulting bit vectors are used to drive the inputs of the DUT, or
  compared to the expected output." That is a value evaluator, not a behavioural
  semantics.

## 2. Style

- **Informal + by-translation + type system.** The key semantic paragraph (§III, after
  Listing 1):
  > In Spade, the behavior of a circuit is described in a cycle-to-cycle manner. The new
  > value of a register in the design is given as an expression of the register values in
  > the current clock cycle. All variables in Spade are immutable: they can only be
  > assigned once. Single assignment is possible because Spade is an expression-oriented
  > language ... the use of immutable variables and expression-based control flow is
  > closer to the resulting hardware where variables correspond to wires and "control
  > flow" is implemented with multiplexers.
  And: "Registers are, together with writes to memories, the only sequential constructs in
  the language, everything else describes combinatorial circuits."
- **Type-system content:** static typing with inference (§III-B); widening arithmetic with
  mandatory `trunc` ("Spade prevents accidental overflow by using the largest possible
  values for most arithmetic operations"); enums with payload, `match` (Listing 5, Fig. 2:
  discriminant bit + payload bits, payload "undefined otherwise"); **linear types for
  `&mut` wires and ports** (§IV) — the one piece of the paper that is a semantic
  *guarantee*: "Each resource of linear type must be consumed exactly once each clock
  cycle."
- Design stance (§V): "prefer emitting errors over potentially surprising behavior".

## 3. Time model

- **Cycle-to-cycle, synchronous, one explicit clock per register.** Listing 1 line 4:
  `reg(clk) counter reset(rst: 0) = if counter == max { 0 } else { trunc(counter + 1) };`
  "the new value of a register ... is given as an expression of the register values in
  the current clock cycle". Output is the last expression of the body (line 11,
  `counter > (max >> 1)`), a combinational function of the register.
- **Pipelines are stage-indexed time** (§III-A, Listing 2, Fig. 1):
  - `pipeline(4) X(clk, a, b) -> int<33>`: "depth, in this case 4, which is the number of
    registers in the pipeline and therefore the delay between input and output. While
    the compiler can infer the depth, it has to be specified manually because it is part
    of the public API."
  - `reg;` — "In a pipeline, the reg-statement tells the compiler to insert a pipeline
    stage, registering all the values visible above it. After the reg-statement on line
    7, any references to p will refer to a delayed version of the value." `reg * 3`
    inserts three stages "without any new computations".
  - Sub-pipeline instantiation `inst(3) subpipe(clk, a)`: the depth is checked against
    the callee's declared depth; "The compiler also checks the availability of variables
    from sub-pipelines, giving an error if the result is used before it is ready"
    (Listing 3: "Use of x before it is ready ... Is unavailable for another 2 stages ...
    Requesting x from stage 1 ... But it will not be available until stage 3").
  - `'initial` names a stage; `stage(initial).a` / `stage(-2)` "is used to bypass some
    pipeline registers and to refer directly to a signal as it appears in another stage
    ... Stage references can refer to both 'future' and 'past' stages".
  - Retiming claim: "In a pipeline without feedback a developer can easily add and remove
    pipeline stages as needed without altering the output value of the pipeline"; with
    feedback "some manual care is required to ensure correct computation".
  So a name in a pipeline denotes a *family* of values indexed by stage; `reg` shifts the
  index by one; `stage(k)` selects an index explicitly. This is a purely static,
  syntactic time model — no events, no delta cycles (those exist only in the external SV
  simulator).
- **One value per signal per cycle** by single assignment + immutability.

## 4. State

- **Registers are explicit** (`reg(clk) name reset(rst: v) = expr`); "Registers in Spade
  are explicit constructs rather than being inferred from the use of something like
  rising_edge." Pipeline stage registers are implicit *in number* (one per `reg;` per
  live value) but explicit in *placement*.
- **Reset value:** syntactic, in the declaration (`reset(rst: 0)`). Power-on without reset
  not discussed.
- **Memories** (§III-C): explicit `clocked_memory` (fixed set of write ports) and
  `read_memory` entities from the standard library, "handled separately" by the compiler;
  "unlike VHDL and Verilog, memories are explicitly instantiated as memories, rather than
  inferred from the structure of the code." Motivation: the whole-register-next-value rule
  "becomes problematic when working with memory-like structures in which only a small
  part of the total state is updated in each cycle."
- **Scoping**: "variables are only visible below their definition which makes it more
  difficult to accidentally create combinatorial loops"; explicit `decl` for forward
  references.

## 5. Intra-cycle ordering

- **None to specify for values**: single assignment, expression-oriented; `if`/`match` are
  muxes (Fig. 2).
- **Mutable wires and ports (§IV)** are where ordering/driver questions appear, and Spade
  answers with a type system rather than a semantics: `&mut T` wires are set with `set
  wire = value` (Listing 6 line 20, 27); "A unit returning a mutable wire expects a value
  to be set for that wire, otherwise the value of the wire may be undefined, or if it is
  set conditionally, a latch could be inferred. Similarly, if a wire is driven by multiple
  drivers, conflicting values may cause issues. While it is possible to catch this in
  simulation, it is better to let the compiler catch such errors." Affine types would give
  "at most once"; "to ensure that all mutable wires are set exactly once, the stronger
  notion of linear types is required, and implemented in Spade." Algorithm (Fig. 3,
  Listing 7): a tree per linear resource (leaves = primitive wires, non-leaves = tuples /
  structs); aliases point into it; `set` or passing to a unit marks consumed; double mark
  → error; final pass: unconsumed leaf → "resource of linear type which was not set".
  "Because Spade describes behavior in a cycle-to-cycle manner, the implementation of a
  linear type system is easier than in the general case."
- **Combinational loops:** discouraged by scoping; allowed via `decl`.
- `&` (immutable) wires: "can be used to pass values via units without them being delayed
  in pipelines" — i.e. a bypass around the stage-indexing.

## 6. Properties stated and how established

- **Linear-type guarantee** (exactly-once set per cycle), by the algorithm of §IV; stated,
  not proven, no evaluation.
- **Pipeline depth/availability checking**: compile-time error on use-before-ready
  (Listing 3) and on depth mismatch at `inst(n)`.
- **No differential testing, no proofs, no evaluation section.** There is no second
  semantics to compare the SV against; the SV is the semantics. Tests are cocotb tests
  of the generated SV, per design.

## 7. Relation between the semantics and the generated Verilog

- Identity: Spade *means* its SystemVerilog. §V-B: "There is limited effort to generate
  Verilog similar in structure to the input Spade code. However, the compiler does attempt
  to keep names readable, and has functions for mapping names and expressions back to
  their source location"; Swim translates VCD values back to Spade types.
- No correctness statement is possible or needed in their framing. (Contrast Copper, which
  has two executable sides and makes their agreement the correctness bar.)

## 9. Transfer to Copper — what fits, what does not

**Fits:**

- **`reg;` is the cleanest published statement of what Copper's `clk.tick().await` does to
  locals.** "Registering all the values visible above it. After the reg-statement, any
  references to p will refer to a delayed version of the value." Copper's "every value live
  across an await becomes a register" is the same operation with *liveness* instead of
  *visibility* deciding the set. Copper could present tick exactly this way: names after
  a tick denote the one-cycle-delayed values of the names before it; `infer_registers`
  computes the set Spade reads off syntactically. Spade's use-before-ready error (Listing
  3) is the dual: Spade *refuses* a use whose register is missing; Copper *inserts* the
  register. Both are decidable on the source without simulation — Copper's
  `copper-analysis` runs on `syn::ItemFn` the way Spade's checks run on HIR.
- **Stage-indexed naming shows that a time-indexed denotation is natural.** Spade's
  `stage(k).x` is "the value of `x` in stage `k`". A Copper semantics can index every local
  by `(iteration, segment)` and define the register map as the identity on names with
  index shifted by one segment. That gives a precise place to say what "one value per
  signal per cycle" means for a local that is *redefined* within a segment (each `let` is
  a fresh name; the register holds the last definition before the tick).
- **Spade's `&mut` wire hazards are Copper's plain-`Out` hazards, one for one:** not set →
  undefined / hold; set conditionally → latch; set twice → conflict. Spade's answer is a
  type rule (set exactly once per cycle). Copper's answers: sequential `Out` unwritten →
  *hold* (defined, by a `<port>_hold` register); conditional write on the register-free
  linear route → the e15 probes found Verilator refusing a latch, so the form is now
  refused (`linear_out_write_anchor_mismatch` restated by form, §10.8); multiple writes →
  last-write-wins on the taken path. Spade is a useful contrast: it forbids the shape;
  Copper defines it. If Copper wants a *typing* presentation of the pretick family, Spade's
  "exactly once per cycle" linearity is the template (a per-cycle resource discipline).
- **Explicit memories with a fixed set of ports** is Copper's `Memory` first-class
  construct (ReadFirst/WriteFirst, port ABI in RECEIVED_MEMORY_ABI.md). Same motivation
  sentence (partial update of large state).
- **Depth as part of the public API** is a precedent for Copper's `RegOut` vs `Out` being
  part of a module's *interface* contract (a `RegOut` adds a cycle), and for the sweep's
  cross-module checks.

**Does not fit, and why:**

- **No imperative sequencing, no mutation, no control flow across cycles.** Spade pipelines
  are feed-forward; feedback is manual; an FSM is an explicit `reg` + `match` (Listing 1
  is that). There is no analogue of a `while` with ticks inside, of `control_extract`, or
  of a `pc`. Spade's "semantics" is therefore the equational one (same as CλaSH/Chisel):
  each register's next value is one expression of current values. Copper's source form is
  richer; Spade only matches Copper's *extracted* form.
- **No point-of-read.** An input name inside a stage denotes its value in that stage's
  cycle; there is no "read the input now, then update a register, then write the output"
  sequence. Opening/closing anchors, `Immediate` reads, `trailing_*_reads_input` have no
  Spade analogue.
- **No simulator of its own ⇒ no sim/SV gap.** Spade's stance ("the SV is normative") is
  the opposite of Copper's current normative document (SYNCHRONOUS_SEMANTICS.md, with the
  simulator as the reference and the SV checked against it). Copper should decide and
  state *which side is normative* and which is verified; the Spade position is a valid
  alternative (the denotation is the SV; the simulator must match) and arguably the one
  Copper's lowering already treats as ground truth whenever a divergence is settled by a
  Verilator reference. Either way, the thing Spade cannot have — an independent executable
  meaning — is Copper's main asset and should be stated as such.
- **Linear types need an explicit resource; Copper's resource is implicit.** Spade can
  count sets because a `&mut` wire is a value. Copper's plain `Out` is a port written by
  statements in a sequential body; "exactly once per cycle" would need to be "exactly
  once per segment on every path", which is the *definite assignment* rule Copper
  deliberately rejected for sequential modules (hold semantics; memory
  "copper_out_hold_semantics"). So the type-system route is only available for
  combinational modules or for a new port kind.
