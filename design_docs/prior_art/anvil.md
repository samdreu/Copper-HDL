---

## 0. One-paragraph verdict

Anvil's formal semantics (App. C.2) is an **execution-log semantics with no
values**: a term denotes a *set* of logs `L = ⟨α0, …, αk⟩`, one finite **set of
actions per cycle** (`ValCreate`, `ValUse`, `RegMut`, `ValSend`, `ValRecv`),
generated by big-step inference rules `Γ; I, M ⊢ t ⇝ L ◁ v`. Values are opaque
identifiers carrying a *dependency set* of registers; register mutation is the
bare action `RegMut(r)`; both branches of an `if` are always possible logs
(E-IfThen / E-IfElse, no condition value); sends and receives may be delayed
by any `k ∈ N`. The semantics therefore over-approximates all possible timings
and says nothing about data. On top of it sits an **event-graph type system**
(C.3): types are lifetimes `(e_l, S_d)` over nodes of a DAG whose labels (`0`,
`#k`, `π.m`, `&c`, `⊕`) constrain a family of *timestamp functions* `τ_G`
(Def. C.9); `≤_G` means "for every timestamp function" (Def. C.11). The
theorem (C.20) is **timing safety**: for every value there is one contiguous
window containing all its uses and all lifetimes promised on sends, inside the
lifetime guaranteed by receives, during which no register it depends on is
mutated (Def. C.15). Proven on paper (App. D) with explicitly sketchy steps.
Functional meaning is delegated to the SystemVerilog lowering (§6.2), which has
no correctness statement; validation is unit tests and synthesis numbers (§7).

## 1. Object given a semantics; grammar

**Object:** a *core calculus*, in two layers.

- **Fig. 7 (p.10), "Anvil syntax"** — the per-process concrete core:

```
process definition  P ::= proc p (π, …) { B }
process body        B ::= ∅ | reg r : δ; B | ch c (π, π); B
                        | spawn p (π, …); B | loop { t } B
term                t ::= true | false | () | cycle N | x | *r
                        | t ⇒ t                       (wait, written >> in source)
                        | let x = t in t
                        | ready (π.m)
                        | if x then t else t
                        | send π.m (x) | recv π.m
                        | r := t                      (set r := t in source)
                        | t ★ t | ◇t                  (binary / unary operators)
δ ∈ data-types   ★ ∈ binary-operators   ◇ ∈ unary-operators
π ∈ endpoints    x ∈ identifiers   r ∈ registers   m ∈ messages
c ∈ channels     p ∈ processes     N ∈ ℕ
```

- **Fig. 10 (p.19), "Anvil abstract syntax"** — the CSP-style program layer used
  by the proofs:

```
message definitions  M ::= { π.m : p, … }        (message ↦ duration requirement)
message set          Σ ::= { π.m, … }
composition          κ ::= t | κ ∥_Σ κ
program              P ::= (loop{t}, M) | P ∥_Σ P
```

Durations `p ::= #N | π.m` (fixed cycles, or "the next send/receive of
message π.m"); event patterns `e ▷ p`; a lifetime is `[e_start, S_end)` with
`S_end` a *set* of patterns, the earliest of which ends it (§5.1–5.2).

**What the formal fragment drops** relative to §4: `recursive { … }` threads
(§4.3), multiple `loop` threads per process (the abstract program has exactly
one `loop{t}` per process), channel definitions with sync modes
`@dyn / @#N / @#m+N` (§4.1), `spawn`, data types, and the `;` parallel
operator — which is **absent from the Fig. 7 grammar yet typed by (T-Join)**
and has no E-rule at all. Likewise Fig. 7 writes `if x then t else t`
(identifier condition) but (T-Cond)/(E-IfThen) take `if t1 then t2 else t3`.
These are small, but they mean the "formal fragment" is not quite closed.

## 2. Style of the semantics

**Primary: big-step operational (relational), generating per-cycle action
logs, non-deterministic, valueless.** Def. C.2 defines `Γ; I, M ⊢ t ⇝ L ◁ v`
("L is a local execution log of t, yielding value name v"); `I` is the set of
value names the derivation may allocate (threaded for freshness), `Γ` maps
`let`-bound names to `(delay, value)`. Def. C.3 composes logs of parallel
processes by cycle-wise alignment with send/recv pairs cancelling (CSP-style
hiding). Def. C.4/C.5 give programs a meaning by **unrolling** `loop{t}` into
`t ⇒ t ⇒ …` and taking prefixes. "The semantics of those constructs is then
defined by their sets of execution logs, which captures all their possible
behaviours" (C.2).

**Secondary: type system, with meaning-by-translation to SV.** The event graph
(§5.3, C.3) is both the typing environment and the compiler IR ("The compiler
uses the event graph as an intermediate representation (IR) throughout the
compilation process", §6). The user-facing semantics is the SV the compiler
emits (§6.2); nothing links it to the log model.

Not present: a denotational stream semantics; a small-step machine; any
value-level evaluation; an axiomatic treatment.

## 3. Time model

- **Explicit cycle index.** `L = ⟨α0, α1, …, αk⟩`, "αi represents the set of
  operations performed during cycle i" (C.2). Composition aligns `αi` with
  `βi` for the same `i`.
- **Within a cycle, actions form a set** — unordered, no sub-cycle phases, no
  delta cycles. The unit of observation is "which actions happened in cycle
  i", not "which value a signal carried".
- **How time advances in a term:**
  - `cycle #k` ⇝ `∅^{k+1} ∘ ⟨{ValCreate(v,∅,∅)}⟩`: k empty cycles, then the
    unit value appears in cycle k. (E-Cycle)
  - `r := t` ⇝ `L ⊎ ⟨{ValUse(v), RegMut(r)}, {ValCreate(v',∅,∅)}⟩`: the
    mutation is logged in the cycle `t` *starts* (merged at index 0 of L via
    ⊎), and the result value `v'` exists from the **next** cycle. The prose:
    "set r := t and set r := t; cycle 1 are equivalent, since register
    assignment takes one cycle to complete" (§4.5). (E-RegAssign)
  - `t1 ⇒ t2` ⇝ `L1 ∘ L2` where `∘` **overlaps** the last cycle of L1 with the
    first of L2: `⟨α0..αk⟩ ∘ ⟨β0..βl⟩ = ⟨α0, …, (αk ∪ β0), β1, …, βl⟩`. So
    `>>` itself costs zero cycles; t2 begins in the cycle t1 completes.
    (E-Wait)
  - `let x = t1 in t2` and `if` ⇝ `L1 ⊎ L2`: **parallel** merge from cycle 0
    (`⊎` is pointwise union). The bound `x` records `(|L1| − 1, v1)` = how
    many cycles until v1 is available; `x` as a term then yields
    `∅^{k+1}` — k empty cycles then nothing (E-Ref), i.e. referencing a
    not-yet-ready value waits for it. `shift(Γ, k)` decrements these delays
    after a wait. (E-Let, E-Ref)
  - `send` ⇝ `∅^{k+1} ∘ ⟨{ValSend(π.m, v, M(π.m)), ValCreate(v',∅,∅)}⟩` for
    **any** `k ∈ ℕ`; `recv` likewise with `∅^k ∘ ⟨{ValRecv(...),
    ValCreate(u, ∅, {v})}⟩`. The delay is unconstrained in the local
    semantics; composition (C.3) fixes it by requiring the partner's action in
    the same cycle. (E-Send, E-Recv)
- **Type-level time: the event graph** `G = (V, E)`, each node `e` labelled
  `G(e) = ⟨ω, preds⟩`, with `ω ∈ {0, #k, π.m, &c, ⊕}`. A **timestamp function**
  `τ_G : V → ℕ` (Def. C.9) must satisfy: root `0 ↦ 0`; `#k ↦ max over preds of
  (τ + k)`; message `π.m ↦ ≥ max of preds` (any later cycle); branch `&c`: of
  the two nodes labelled `&c` exactly one gets `max of preds`, the other ∞;
  join `⊕ ↦ min of preds`. Patterns: `τ(e ▷ #k) = τ(e) + k`; `τ(e ▷ π.m)` =
  timestamp of the earliest `π.m`-labelled node strictly after `e` (∞ if none)
  (Def. C.10). **`a ≤_G b` iff `τ(a) ≤ τ(b)` for all timestamp functions**
  (Def. C.11). This is the device that makes "dynamic timing" statically
  checkable: a type is a constraint on a *family* of concrete schedules.
- **Lifetime** (type): `T ::= (e_l, S_d)` — start node and set of end patterns,
  empty set = eternal (C.3).

## 4. State: registers vs wires/values, initial values

- **Registers are explicitly declared** (`reg r : δ` in the process body) and
  are the *only* mutable things. `*r` reads; `set r := t` writes. "Anvil's type
  system exposes [registers and signals] fully" (abstract); "Unlike HLS
  languages that abstract away registers and cycle latencies, Anvil gives the
  designer full control over register mutations and cycle latencies" (§3).
- **Everything else is an immutable named value** with a dependency set:
  `ValCreate(v, {r1..rm}, {v1..vn})` "creating a value with name v that depends
  on registers r1..rm and values v1..vn" (Def. C.1). `*r` creates a value that
  depends on `{r}` (E-RegEval); a received message creates a value depending
  on the received one (E-Recv); literals and `cycle` depend on nothing. A
  binary operator's lifetime is the intersection (`S1 ∪ S2` of end patterns,
  T-BinOp) — the paper's "the signal (ptext ^ r1_key) + noise has a lifetime
  that is the intersection of the lifetimes of ptext, r1_key, and noise" (§5.2).
  Note the formal E-rules have **no case for `t1 ★ t2`** (only T-BinOp exists),
  another closure gap.
- **What decides "stateful":** the declaration. There is no inference. A
  `let`-bound value lives as long as its lifetime, which the type system
  computes; the compiler must then realise a multi-cycle `let` as a register
  (§6.2 mentions registers "to record the current state" for joins, cycle
  delays, and send/receive completion — not for `let` values; how a value
  used two cycles later is held is not described).
- **Register read/write timing** is fixed by the rules: a read at `e_c` sees
  the register at `e_c` (T-RegEval types `*r : (e_c, S_d)`); a write at `e_c`
  takes effect at `e_c ▷ #1` (T-RegAssign result type `(e_l', ∅)` with
  `G(e_l') = ⟨#1, {e_c}⟩`). This is nonblocking-assignment timing stated as a
  rule.
- **Loan time** `R(r)`: the set of intervals during which some live value
  depends on `r`; "For each interval included in the loan time, r should not
  be mutated" (§5.2). The paper calls this "loaned register" in error messages
  ("Error: Attempted assignment to loaned register", Fig. 2).
- **Initial / reset values: not discussed anywhere** in the formal part. The
  SV in Listing 2 (App. A) has `initial` blocks, the Anvil in Listing 1 has
  `reg cnt : logic[32]` with no initializer, and §6.2 does not say what the
  generated `always_ff` resets to. Timing safety as defined is independent of
  values so the gap does not affect the theorem — but a Copper reader should
  note that "power-on value" is outside the model.

## 5. Intra-cycle ordering

- **Actions in a cycle are a set; there is no statement order inside a
  cycle.** `;` is parallel ("t1; t2 initiates both term evaluations in
  parallel", §4.5), `let`/`if` merge logs from cycle 0, and `>>` is the only
  sequencing — which merges its boundary cycle. Program text order inside one
  cycle does not exist as a concept.
- **Reads see the pre-mutation register value; writes land next cycle.** From
  §5.4's worked example: "e5 and e7 are adjacent cycles in which the register
  can carry different values" (assignment starts at e5, completes at e7 = e5 ▷
  #1). So within a cycle "read-then-write" and "write-then-read" are the same
  thing: the read is of the current value, the write is of the next. This is
  Verilog `<=` made the only option.
- **Forwarding:** none. A value computed from `*r` in cycle i keeps that
  value (it is immutable) — the hazard Anvil targets is that *r* is mutated in
  cycle i+1 while the *hardware signal* that computes from `*r` is still being
  used (because in RTL the "value" is really a wire that follows the
  register). Safety says: no `RegMut(r)` in `[a, b)` for any `r` in the
  dependency set while `v` is in use.
- **Multiple writes to one register in one cycle:** not addressed in the
  formal fragment (one thread per process). The concrete language permits
  several `loop` threads per process ("Each process contains one or more
  threads that execute concurrently", §4.3) and nothing in §4–§6 says what two
  threads writing the same register in the same cycle mean; presumably the
  compiler rejects or priorities, but the paper does not say. Loan time would
  catch a write while *another value depends on it*, not two writes.
- **Last-write-wins / priority:** not a concept.
- **Combinational loops:** not addressed. Related work treats BaseJump / Wire
  Sorts as "a separate concern than timing hazards" (§8). Message sync mode
  `@#0`-style static modes could create same-cycle paths across processes;
  not discussed.
- **Cross-process same-cycle communication:** C.3 requires `ValSend ∈ αi` iff
  `ValRecv ∈ βi` — send and receive are *simultaneous* ("akin to unbuffered
  channels in Go", §4.1). Received values are therefore available in the same
  cycle they are sent, i.e. combinational across the module boundary unless
  the sync mode inserts delay. This is the only intra-cycle ordering
  constraint in the model.

Observations:

- **Nothing is mechanized**; the proofs are a page each and lean on "It is
  obvious", "By induction", "easily follows". Lemma D.1's existence argument
  ("k linear equations, each with at least one unique variable, hence a
  solution exists") is hand-waved and is doing real work (the ∞ timestamps for
  untaken branches, the `≥` for message nodes).
- **The implementation uses "sound approximations of ≤_G and <_G"** (C.3) —
  so the implemented checker is stricter than the theory; no statement of
  what the approximation is.
- **Determinism, races, multiple writers, combinational loops, functional
  correctness, equivalence with generated hardware:** none claimed.
- The **safety property is only about timing**: "all uses of a value v and the
  lifetime promised to the environment should fall within a continuous time
  window ... during this time window, values received from the environment
  through receive are live, and no register that v depends on is mutated"
  (C.4). It does not say the value is *correct*, only *steady*.
- Well-typedness of a process is well-typedness of `t ⇒ t` (Def. C.7) — a
  loop is checked by typing two unrolled iterations, which is what makes the
  back-edge hazards (a write at the end of iteration k vs a read at the start
  of k+1) visible to a DAG-based checker.

## 7. Relation to the generated hardware

- §6.2 **Code generation**: process → SV module; each message → up to three
  ports `data / valid / ack` (valid/ack omitted when the sync mode is static or
  dependent); each event → a one-bit wire `current`; registers only for joins
  ("which predecessors have been reached"), cycle delays ("cycle count"), and
  dynamic send/receive ("whether the message has been sent or received"). "the
  compiler generates no extra code for maintaining lifetimes or enforcing
  timing safety".
- **No correctness theorem for the lowering**, and no statement relating the
  SV's behaviour to the execution-log model. The event graph is simultaneously
  the typing environment and the IR, so the relation "type system ↔ FSM" is
  by construction rather than by proof.
- **Event-graph optimizations** (§6.1, Fig. 8): merging identical outbound
  labels, removing unbalanced joins, shifting branch joins, removing branch
  joins — "while keeping its semantics unchanged", with no definition of the
  semantics being preserved beyond "two events can be merged if they always
  occur at the same time".
- **Validation (§7):** functional equivalence to the SV baselines by "unit
  tests" (FIFO, spill register, stream FIFO, AXI routers, AES) and "baseline
  RISC-V smoke tests" (CVA6 TLB/PTW); synthesis on a 22 nm ASIC flow for
  area/power/f_max; "none of the designs introduce extra cycle latency".
  There is no Anvil simulator; the only executable artefact is the SV. So, as
  for Filament, "model ≡ hardware" is not a question the paper can ask —
  there is one realization, not two.
- §7.2 / App. B: the evaluation's safety story is anecdotal (the stream FIFO
  relies on SVA warnings; GitHub issues that Anvil "could have prevented").
- App. A: bounded model checking (Yosys SMT-BMC + z3) on the SV version of
  Listing 1 "fails to detect the violation even with large depth limits" —
  used to argue for the language-based approach.

### 8.1 Execution logs (Def. C.1, C.2 and the key E-rules; pp.19–20)

```
L = ⟨α0, α1, …, αk⟩     αi = finite set of actions in cycle i, each of the form
  ValCreate(v, {r1..rm}, {v1..vn})   new value v depending on registers ri and values vj
  ValUse(v)                          use of v
  RegMut(r)                          mutation of register r
  ValSend(π.m, v, p)                 send v on message π.m with duration p
  ValRecv(π.m, v, p)                 receive v on π.m with duration p

Operators:
  ⟨α0..αk⟩ ∘ ⟨β0..βl⟩ = ⟨α0, …, αk ∪ β0, β1, …, βl⟩        (sequence; boundary cycle shared)
  ⟨α0..αk⟩ ⊎ ⟨β0..βl⟩ = ⟨α0∪β0, …, αk∪βk, βk+1, …, βl⟩    (parallel, k ≤ l)
  ∅^k = ⟨∅, …, ∅⟩ (k copies)
  shift(Γ, k): every (x : (k', v)) becomes (x : (max(0, k'−k), v))

Judgement:  Γ; I, M ⊢ t ⇝ L ◁ v
  Γ : let-bound x ↦ (cycles until ready, value name);  I : value names allocated;
  M : message ↦ duration requirement

(E-Cycle)      Γ; {v}, M ⊢ cycle #k ⇝ (∅^{k+1} ∘ ⟨{ValCreate(v,∅,∅)}⟩) ◁ v

(E-Literal)    Γ; {v}, M ⊢ n ⇝ ⟨{ValCreate(v,∅,∅)}⟩ ◁ v

(E-Wait)       Γ; I1, M ⊢ t1 ⇝ L1 ◁ v1     Γ; I2, M ⊢ t2 ⇝ L2 ◁ v2     I1 ∩ I2 = ∅
               ──────────────────────────────────────────────────────────────────
               shift(Γ, |L1| − 1); (I1 ∪ I2), M ⊢ t1 ⇒ t2 ⇝ (L1 ∘ L2) ◁ v2

(E-Let)        Γ; I1, M ⊢ t1 ⇝ L1 ◁ v1     Γ, x : (|L1| − 1, v1); I2, M ⊢ t2 ⇝ L2 ◁ v2
               I1 ∩ I2 = ∅
               ──────────────────────────────────────────────────────────────────
               Γ; (I1 ∪ I2), M ⊢ let x = t1 in t2 ⇝ (L1 ⊎ L2) ◁ v2

(E-Ref)        Γ(x) = (k, v)
               ─────────────────────────────
               Γ; ∅, M ⊢ x ⇝ ∅^{k+1} ◁ v

(E-RegAssign)  Γ; I, M ⊢ t ⇝ L ◁ v     v' ∉ I
               ─────────────────────────────────────────────────────────────────────────────
               Γ; I ∪ {v'}, M ⊢ r := t ⇝ L ⊎ ⟨{ValUse(v), RegMut(r)}, {ValCreate(v',∅,∅)}⟩ ◁ v'

(E-Send)       Γ; I, M ⊢ t ⇝ L ◁ v     v' ∉ I     k ∈ ℕ
               ────────────────────────────────────────────────────────────────────────────────
               Γ; (I ∪ {v'}), M ⊢ send π.m(t) ⇝ ∅^{k+1} ∘ ⟨{ValSend(π.m, v, M(π.m)), ValCreate(v',∅,∅)}⟩ ◁ v'

(E-Recv)       k ∈ ℕ,  u ≠ v
               ───────────────────────────────────────────────────────────────────────
               Γ; {v, u}, M ⊢ recv π.m ⇝ ∅^k ∘ ⟨{ValRecv(π.m, v, M(π.m)), ValCreate(u, ∅, {v})}⟩ ◁ u

(E-IfThen)     Γ; I1, M ⊢ t1 ⇝ L1 ◁ v1   Γ; I2, M ⊢ t2 ⇝ L2 ◁ v2   Γ; I3, M ⊢ t3 ⇝ L3 ◁ v3
               I1 ∩ (I2 ∪ I3) = ∅   I2 ∩ I3 = ∅
               ────────────────────────────────────────────────────────────────────────
               Γ; (I1 ∪ I2 ∪ I3), M ⊢ if t1 then t2 else t3 ⇝ L1 ⊎ L2 ⊎ ⟨{ValUse(v1)}⟩ ◁ v2
(E-IfElse)     same premises, conclusion … ⇝ L1 ⊎ L3 ⊎ ⟨{ValUse(v1)}⟩ ◁ v3

(E-RegEval)    ∅; {v}, M ⊢ *r ⇝ ⟨{ValCreate(v, {r}, ∅)}⟩ ◁ v
(E-Ready)      ∅; {v}, M ⊢ ready(π.m) ⇝ ⟨{ValCreate(v,∅,∅)}⟩ ◁ v
```

Notes on the rules as written: (E-Send)'s send is delayed `k+1 − 1 = k`
cycles after the operand's log *is not* sequenced — the rule drops `L`
entirely from the conclusion (the operand's log does not appear in the
output), which looks like a typo (should be `L ∘ ∅^{k+1} ∘ …` or `L ⊎ …`).
(E-RegAssign) uses `L ⊎ ⟨…⟩`, placing `RegMut` in cycle 0 of `L`, i.e. *the
cycle the assignment term starts*, not the cycle `t` finishes — consistent
with `*r` and `let` being zero-cycle, but surprising if `t` were `cycle 2`.
The branch rules carry no condition value, so both are always derivable.

### 8.2 Event graph, timestamps, ≤_G (C.3, C.3.1)

```
G = (V, E) a DAG;  G(e) = ⟨ω, {e' | e' → e ∈ G}⟩,  ω ∈ {0, #k, π.m, &c, ⊕}
Type   T ::= (e_l, S_d)     start node, set of end patterns e ▷ p (∅ = eternal)
Pattern  e ▷ #k  |  e ▷ π.m      (k cycles after e | first π.m after e)

Def. C.9 (Timestamp)  τ_G : V → ℕ is a timestamp function of G if ∀ e ∈ V:
  G(e) = ⟨0, S⟩      ⟹ τ(e) = 0
  G(e) = ⟨#k, S⟩     ⟹ τ(e) = max_{e'∈S} (τ(e') + k)

  G(e) = ⟨&c, S⟩ ∧ τ(e) = max_{e'∈S} τ(e')  ⟹  every OTHER node labelled ⟨&c, S⟩ has τ = ∞
  G(e) = ⟨⊕, S⟩      ⟹ τ(e) = min_{e'∈S} τ(e')

Def. C.10   τ(e ▷ #k) = τ(e) + k
            τ(e ▷ π.m) = min { τ(e') | G(e') = ⟨π.m, S⟩, τ(e) < τ(e') }   (∞ if none)

Def. C.11   a ≤_G b  iff  ∀ timestamp functions τ_G: τ(a) ≤ τ(b);   a <_G b likewise with <.

### 8.3 Typing rules (C.3, p.21–22) — the ones that carry the timing content

```
Judgement  Γ; G, R, M, C, e_c ⊢ t : T
  Γ : let-bindings ↦ type;  G : event graph;  R : register ↦ loan time (set of (e, S));
  M : π.m ↦ duration;  C : branch-condition identifiers used;  e_c : node = "now"

(T-Cycle)      G(e_l) = ⟨#k, {e_c}⟩
               ───────────────────────────────────
               ∅; G, R, M, ∅, e_c ⊢ cycle k : (e_l, ∅)

(T-Wait)       Γ; G,R,M,C1, e_c ⊢ t1 : (e_l, S_d)     Γ; G,R,M,C2, e_l ⊢ t2 : T2     C1 ∩ C2 = ∅
               ──────────────────────────────────────────────────────────────────────────
               Γ; G,R,M, C1 ∪ C2, e_c ⊢ t1 ⇒ t2 : T2
               (t2 is typed "at" the node where t1's value starts)

(T-Recv)       M(π.m) = p     G(e_l) = ⟨π.m, {e_c}⟩
               ────────────────────────────────────────────
               ∅; G,R,M,∅, e_c ⊢ recv m : (e_l, {e_l ▷ p})

(T-Ref)        x : (e_l, S_d) ∈ Γ     G(e_l') = ⟨#0, {e_c, e_l}⟩
               ────────────────────────────────────────────────
               Γ; G,R,M,∅, e_c ⊢ x : (e_l', S_d)
               (a reference is ready at max(now, when x became ready))

(T-Send)       Γ; G,R,M,C, e_c ⊢ t : (e_l, S_d)     G(e_l') = ⟨π.m, {e_c}⟩
               e_l ≤_G e_c     e_l' ▷ M(π.m) ≤_G S_d
               ────────────────────────────────────────────────
               Γ; G,R,M,C, e_c ⊢ send π.m(t) : (e_l', ∅)
               (operand already live now; its lifetime outlasts the contract after the send completes)

(T-BinOp)      Γ;…,C1,e_c ⊢ t1 : (e1,S1)   Γ;…,C2,e_c ⊢ t2 : (e2,S2)   G(e_l') = ⟨#0,{e1,e2}⟩   C1∩C2=∅
               ─────────────────────────────────────────────────────────────────────────────
               Γ; G,R,M, C1∪C2, e_c ⊢ t1 ★ t2 : (e_l', S1 ∪ S2)

(T-RegAssign)  Γ; G,R,M,C, e_c ⊢ t : (e_l, S_d)
               ∀ (e, S) ∈ R(r):  e_c <_G e  ∨  S ≤_G e_c          ← not inside any loan interval
               e_l ≤_G e_c     e_c ▷ #1 ≤_G S_d                   ← operand live now and for one cycle
               G(e_l') = ⟨#1, {e_c}⟩                              ← result exists next cycle
               ──────────────────────────────────────────────────
               Γ; G,R,M,C, e_c ⊢ r := t : (e_l', ∅)

(T-RegEval)    ∃ (e, S) ∈ R(r):  e ≤_G e_c  ∧  e_c ≤_G S_d  ∧  S_d ≤_G S
               ──────────────────────────────────────────────────────
               ∅; G,R,M,∅, e_c ⊢ *r : (e_c, S_d)
               (a read's lifetime must sit inside some loan interval of r;
                the loan time R is "guessed" — it is part of the environment, Def. C.6 ∃ R)

(T-Cond)       Γ;…,C1,e_c ⊢ t1 : (e1,S1)    Γ;…,C2,e_c' ⊢ t2 : (e2,S2)    Γ;…,C3,e_c'' ⊢ t3 : (e3,S3)
               e1 ≤_G e_c ∧ e_c ≤_G S1          c ∉ C1∪C2∪C3     C1 ∩ (C2∪C3) = C2 ∩ C3 = ∅
               G(e_c') = G(e_c'') = ⟨&c, {e_c}⟩    e_c' ≠ e_c''     G(e_l') = ⟨⊕, {e2, e3}⟩
               ───────────────────────────────────────────────────────────────────────────
               Γ; G,R,M, C1∪C2∪C3∪{c}, e_c ⊢ if t1 then t2 else t3 : (e_l', S1 ∪ S2 ∪ S3)

(T-Join)       Γ;…,C1,e_c ⊢ t1 : (e1,S1)   Γ;…,C2,e_c ⊢ t2 : (e2,S2)   G(e_l') = ⟨#0,{e1,e2}⟩   C1∩C2=∅
               ─────────────────────────────────────────────────────────────────────────────
               Γ; G,R,M, C1∪C2, e_c ⊢ t1 ; t2 : (e_l', S2)

Def. C.6  t is well-typed under M if ∃ G, R, e0, C, T with G(e0) = ⟨0, ∅⟩ and ∅; G,R,M,C,e0 ⊢ t : T.

## 9. Transfer to Copper — what fits, what does not

### 9.1 Devices that fit

1. **The per-cycle log as a sequence of sets, with an explicit index.** `L =
   ⟨α0, …, αk⟩` is the natural carrier for Copper's "one value per signal per
   cycle": make `αi` a *valued* record (`Signal ⇀ Value`, plus the tagged
   reads/writes if the alignment rules are to be expressible). Anvil's choice
   that `αi` is a **set** (unordered) is exactly the statement Copper needs:
   within a cycle, program order is not part of the meaning. Copper's
   sequential body then has to be *mapped* onto this (the anchor rule), which
   is where Copper's content lives and where Anvil has nothing.

2. **`r := t` as "RegMut now, value from next cycle" and `*r` as "the current
   value".** (E-RegAssign)/(T-RegAssign)/(T-RegEval) are the RegOut rule and
   the "reads see committed state" rule written as inference rules. Copper
   can lift them verbatim for registers and `RegOut`: `write(r) at cycle c`
   logs a mutation at c and defines `r(c+1)`; `read(r) at c` yields `r(c)`.
   The `G(e_l') = ⟨#1, {e_c}⟩` premise is the precise form of "takes effect
   at the first edge after it executes".

3. **Loop meaning by unrolling plus a "two iterations suffice" lemma.**
   (C-Extend) `t' ⇒ t` and Lemma C.19 give a template for Copper's loop body:
   define the denotation of the loop as the limit of `body ⇒ body ⇒ …`, and
   prove/test the alignment rules on `body ⇒ body` only. This is exactly
   what the trailing-drive rules reason about (the second iteration's opening
   reads against the first's trailing writes), and the cut-vertex argument in
   D.4 (the loop head is a cut vertex of the event graph; the second copy is
   a relabelling) transfers to Copper's `Cfg` with its back edge. For the
   extraction route, the `pc` FSM's state at the back edge is the cut vertex.

4. **Event graph with labelled nodes and the "for all timestamp functions"
   quantifier.** Copper's `Cfg` (E_comb = `#0` edges, E_tick = `#1` edges,
   branches = `&c` pairs, merges = `⊕`) *is* an event graph; `check_reachability`
   ("every loop path reaches a tick") is "every cycle in the unrolled graph
   has a `#1` edge". The data-dependent timing of the `match pc` route — a
   wait loop that spins an unknown number of cycles, a `break` out of a
   counted `for` — is what Anvil's `π.m`-labelled nodes (`τ(e) ≥ max preds`)
   and `&c`/∞ model. `≤_G` quantifying over every timestamp function is the
   right way to state a timing property for all runs without a value
   semantics; Copper's phase-sensitive rules (multi_phase_out_write,
   check_memory_staging) are statements of the form "for every schedule
   consistent with the Cfg, write w and read r are in the same/different
   cycle", i.e. `≤_G` facts. Copper should name this quantifier.

5. **Dependency sets on values** (`ValCreate(v, regs, vals)`, `L ⊢ v ↓ D`).
   Copper's anchor analysis asks "does an `In` read comb-reach this write, and
   on which paths?" — that is a dependency set computed on a log, with the
   `In` read as the ValCreate root. Extending `ValCreate` with the *cycle and
   anchor* of each dependency (`{(sig, cycle, opening|closing)}`) would give a
   single object in which "mixed anchors" (D1 clause A) is literally "two
   drives of one port whose dependency sets name different anchors for the
   same signal".

6. **CSP-style parallel composition with send/recv alignment** is the shape
   for Copper's `structural` parent: two module logs aligned cycle-wise, with
   the wires in `Σ` identified and hidden. Copper has no handshake, so `Σ`
   is a set of port pairs and the alignment condition is `out_1(c) = in_2(c)`
   (combinational) — simpler than Anvil's.

7. **"Well-typed process ⟺ well-typed `t ⇒ t`"** is a precise statement of
   front-end parity's object: both front-ends run the same list of rules over
   the same `syn::ItemFn`; the thing they agree on could be stated as
   well-typedness of `body ⇒ body` under one rule set.

### 9.2 Devices that do not fit, and why

1. **No values ⇒ cannot state "sim ≡ SV".** Same as Filament. Anvil's logs
   cannot say which value `out` carried in cycle 3; E-IfThen/E-IfElse are both
   derivable regardless of the condition. The whole Copper correctness bar is
   outside the model. Borrow the carrier (`⟨α0..αk⟩`), put values in it.

2. **No intra-cycle order means the alignment family is not expressible as a
   property of Anvil logs.** In Anvil a cycle's actions are a set and values
   are immutable, so "write Out then read In then write Out again before the
   tick" cannot be written down; `set` is nonblocking by fiat and `let` cannot
   be rebound. Copper's plain `Out` is a *mutable* port written from a
   sequential body — Anvil has nothing mutable except registers, and those
   commit next cycle. So Anvil "solves" D1/multi-phase/linear-anchor by not
   having the construct. The direct port of Anvil's register rule to a plain
   `Out` would make every `Out` a `RegOut`, which is the "option 2 not taken"
   decision (2026-10-21) in reverse: Copper deliberately keeps combinational
   `Out`. Anvil cannot help with *that* semantics; it can only help with the
   registered half.

3. **Outputs are messages with contracts, not continuous ports.** Anvil's
   "lifetime" is a steadiness promise on a handshaked message; a Copper `Out`
   has a value every cycle and holds when unwritten. There is no concept in
   Anvil of "the value of an output in a cycle in which nothing was sent".
   Copper's hold semantics must be stated separately (as a `Out(c) = Out(c−1)`
   default), which Anvil's model has no slot for.

4. **Dynamic timing comes from channel handshakes, not from data.** Anvil's
   "events that may occur arbitrarily late" are `recv`/`send` completions;
   the *data* never decides timing (a branch's `&c` pair is just "one of two,
   unknown which"). Copper's wait loops and `break`s are data-dependent on
   register and input values. The event-graph quantifier over all timestamp
   functions is sound for Copper too (it over-approximates), but it means a
   Copper semantics built this way can only state *timing-shape* facts, not
   "this loop exits after exactly the cycle in which `valid_i` is high".

5. **Registers declared, not inferred**; **values immutable**; **no
   multi-writer story**; **no combinational loops**; **no reset**. Copper
   infers registers by liveness, allows multiple writes to a port within a
   segment (collapsed by `multi_write_collapse` / `last-write-wins` with
   hold), runs a levelized scheduler over comb SCCs, and has a decided
   power-on rule. Each of these would be an *addition* to an Anvil-style
   model, not a borrowing.

6. **Proof bar.** Paper-only, sketched (D.1's linear-equations argument;
   "It is obvious that e1 is a cut vertex"), and the implementation uses
   unstated "sound approximations" of `≤_G`. Not a standard to aim at;
   Copper's differential sweep is a stronger empirical statement than
   anything either paper offers, and should be presented as the *test* of a
   single normative denotation realized twice.

### 9.3 Concrete suggestion

Combine the two papers' carriers and add values:

```
Log       L = ⟨α0, α1, …⟩,  αc : { reg : Reg ⇀ Value,  out : Port ⇀ Value,
                                   in  : In ⇀ Value,   drives : set of Drive }
Drive     = (port, value, anchor)        anchor ∈ { opening(c), closing(c) }
reg(c+1)  = commit of the segment ending at edge c            (Anvil E-RegAssign)
RegOut    = a register port: RegOut(c+1) = last write in segment c, else RegOut(c)
Out(c)    = value of the unique collapsed drive at c, else Out(c−1)   (hold; neither paper)
read of In at anchor opening(c): In(c);  at closing(c): the value at the edge ending c
```

State the loop as `body ⇒ body ⇒ …` (Anvil C-Extend) with `⇒` overlapping
the boundary cycle (Anvil's `∘`), the alignment rules as `≤_G`-style facts on
Copper's `Cfg` quantified over every schedule (Anvil Def. C.9/C.11), and the
correctness bar as `L_sim = L_SV` pointwise on `out` for every input stream —
the sentence neither paper has, and the one the sweep already checks.
